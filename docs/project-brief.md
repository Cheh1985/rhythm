# Ритм — общий контракт проекта

Этот документ — краткий стабильный контекст для поэтапной разработки PWA-дневника тренировок. Полное исходное ТЗ пользователя остаётся главным источником требований; при расхождении этот brief не отменяет явно заданное требование.

## Назначение

«Ритм» — многопользовательское mobile-first приложение для замкнутого цикла:

`план → выполнение → фактические данные → отчёт → анализ во внешнем LLM → новая версия плана`.

Основной сценарий: тренер или ChatGPT создаёт JSON-план, пользователь импортирует его, проводит тренировку на iPhone с быстрым вводом `вес → повторы → RIR`, а затем скачивает структурированный JSON и читаемый Markdown для следующего анализа.

## Приоритеты

1. Надёжность и историчность данных.
2. Минимум действий с телефоном во время подходов.
3. Простая установка на PHP-хостинг, VPS и FASTPANEL.
4. Полноценная работа тренировки без сети.
5. Понятный экспорт для ChatGPT/LLM.
6. История и аналитика.
7. Визуальный polish.

## Технологический контракт

- PHP 8.2+ без обязательного фреймворка и без постоянного Node.js-процесса.
- MySQL 8 или MariaDB, PDO и prepared statements.
- Серверные HTML-экраны, CSS, нативный JavaScript и Fetch API.
- Service Worker, Cache API и IndexedDB для offline/cache/outbox.
- Production-сборка должна работать на обычном PHP-хостинге.
- Основной язык интерфейса — русский; строки и структура не должны мешать будущей локализации.
- Время событий хранится в UTC, timezone пользователя по умолчанию `Europe/Moscow`.

## Неизменяемые принципы данных

- Запланированное, фактически выполненное и предложенное на будущее — разные сущности и разные поля.
- Старые версии программ и импортированные планы не перезаписываются.
- `exercise_id` — стабильный строковый идентификатор и не меняется при переименовании.
- Существенные изменения попадают в audit log; исторически важное удаление — soft delete.
- Все запросы к пользовательским данным ограничиваются `user_id` на сервере.
- Повторная доставка offline-действия идемпотентна.
- Одновременное редактирование защищено optimistic locking/version.

## Главные сущности

- `users`, `login_attempts`;
- `exercises`;
- `training_programs`, `program_versions`, `workout_templates`;
- `workout_plans`, `workout_exercises`;
- `workout_sessions`, `readiness_logs`, `session_exercises`, `exercise_sets`;
- `discomfort_logs`, `progression_suggestions`, `personal_records`;
- `body_measurements`, `swimming_sessions`, `schedules`, `audit_logs`.

План и факт должны быть разделены. Замена упражнения хранит исходный и фактический `exercise_id`, причину и время. Подходы поддерживают `warmup` и `working`; структура предусматривает normal, superset, dropset, rest-pause, cluster и AMRAP.

## Безопасность

- `password_hash()` / `password_verify()`, PHP sessions, regeneration после входа.
- CSRF для всех изменяющих запросов, экранирование HTML, серверная валидация.
- HttpOnly, SameSite и Secure cookie при HTTPS.
- Ограничение попыток входа.
- Максимальный размер upload, проверка расширения, MIME/содержимого и JSON schema.
- Никаких stack trace в production; подробности — только в server log.
- Секреты только в `.env`, который не попадает в Git.

## JSON-контракт

План:

```json
{"schema":"training-plan","schema_version":"1.0"}
```

Отчёт:

```json
{"schema":"training-report","schema_version":"1.0"}
```

Импорт всегда проходит серверную валидацию и превью. Неизвестное упражнение создаётся только после явного подтверждения. Поддержка версий схемы должна быть расширяемой.

## UX тренировки

- Большие touch targets, шрифт input не менее 16 px, safe-area iPhone.
- Никаких широких таблиц на основном экране.
- Следующий подход предзаполняется плановым или последним фактическим весом.
- Кнопки веса `−5`, `−2.5`, `+2.5`, `+5`, повторов `−1`, `+1`, RIR `0…5+`.
- После сохранения подхода запускается rest timer, рассчитанный от timestamp, а не от числа тиков.
- Autosave после каждого существенного действия.
- Оборудование занято, пропуск, замена и дискомфорт сохраняются структурированно.
- Незавершённая тренировка предлагается к продолжению при следующем входе.

## Бизнес-метрики

- Рабочий tonnage: сумма `weight × reps` только для `working` sets.
- e1RM по Epley: `weight × (1 + reps / 30)`; это аналитическая оценка, не реальный максимум.
- Double progression: предложение увеличить вес создаётся, когда все рабочие подходы достигли верхней границы повторений при допустимом RIR. Программа автоматически не меняется.
- Аналитика включает подходы, мышцы, объём, RIR, длительность, PR и измерения, но не объявляет медицинские или категоричные тренировочные выводы.

## Definition of Done любого этапа

- Этап реализован реальными файлами, а не только описанием.
- Проект остаётся запускаемым; нет заведомо мёртвых основных маршрутов.
- Выполнены релевантные автоматические проверки и ручные smoke checks.
- Проверена изоляция пользователей для новых запросов.
- Обновлены `CHANGELOG.md` и `docs/work-status.md`.
- Новые архитектурные решения отражены в `docs/database.md` или `docs/json-format.md`.
- Не затронуты требования будущих этапов без необходимости.
