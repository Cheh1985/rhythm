# JSON-формат плана тренировки

## Контракт training-plan v1.0

Импорт принимает один UTF-8 JSON-объект с точными маркерами:

```json
{"schema":"training-plan","schema_version":"1.0"}
```

Машиночитаемый контракт находится в `docs/training-plan-v1.0.schema.json`, полный рабочий пример — в `tests/fixtures/training-plan/full-body-a.json`. Серверная проверка является источником истины: лишние поля, неявное преобразование строк в числа и неподдерживаемые версии отклоняются. Формат расширяется новой `schema_version`, а не изменением смысла существующих полей.

## Корневой объект

| Поле | Тип | Обязательное | Назначение |
|---|---|---:|---|
| `schema` | string | да | Ровно `training-plan` |
| `schema_version` | string | да | Ровно `1.0` |
| `plan_id` | stable ID | да | Идемпотентный внешний ID конкретного плана; уникален в пределах пользователя |
| `program` | object | да | Идентичность и версия программы |
| `workout` | object | да | Шаблон, дата и тип тренировки |
| `exercises` | array | да | От 1 до 100 упражнений |
| `trainer_notes` | string/null | нет | Заметка тренера до 10 000 символов |
| `pre_workout` | object | нет | `instructions`, `nutrition`, `equipment`, каждое string/null до 2 000 символов |

Stable ID имеет длину 3–190 символов (`exercise_id` и `template_id` — до 80), начинается со строчной латинской буквы или цифры и далее содержит только `a-z`, `0-9`, `.`, `_`, `-`. Идентификаторы не являются названиями и не меняются при переименовании.

## `program`

| Поле | Тип | Правило |
|---|---|---|
| `program_id` | stable ID | Стабильный ID программы в пределах пользователя |
| `name` | string | 1–190 символов |
| `version` | integer | 1–100000 |
| `parent_version` | integer | Запрещён для v1, обязателен для v2+ и меньше `version` |
| `change_reason` | string | Обязательная читаемая причина, 1–1000 символов |
| `description` | string/null | Необязательное описание до 10 000 символов |

Версия неизменяема. Повторный импорт той же пары `program_id + version` разрешён только при идентичном каноническом снимке `program`. Для новой v2+ указанная родительская версия уже должна существовать у того же пользователя. В БД она превращается в `parent_version_id`.

## `workout`

| Поле | Тип | Правило |
|---|---|---|
| `template_id` | stable ID | Стабильный код шаблона внутри версии программы |
| `name` | string | 1–190 символов |
| `type` | enum | `strength`, `swimming`, `cardio`, `mobility`, `other` |
| `scheduled_date` | string | Реальная календарная дата `YYYY-MM-DD` |
| `goal` | string/null | До 5 000 символов |
| `estimated_duration_min` | integer | 1–1440 минут |

Шаблон состоит из `workout` без `scheduled_date` плюс `exercises`. Одинаковый `template_id` внутри одной версии не может иметь другое содержимое. Дата относится к конкретному `workout_plan`, поэтому один неизменяемый шаблон можно назначать на разные даты и с разными `plan_id`.

## Элемент `exercises`

Обязательные поля:

- `exercise_id`: стабильный ID существующего или явно создаваемого упражнения;
- `name`: отображаемое имя до 190 символов;
- `order`: уникальное целое 1–100;
- `sets`: целое 1–20;
- `rep_range`: закрытый объект `{"min":1..1000,"max":1..1000}`, где `max >= min`;
- `target_rir`: закрытый объект с числовыми `min` и `max` от 0 до 10, где `max >= min`;
- `rest_seconds`: целое 0–3600.

Необязательные поля:

- справочник: `category`, `muscles`, `exercise_type`, `equipment`;
- прогрессия: `progression_increment` от 0.01 до 1000, `progression_mode` — `absolute` или `percent`;
- план: `weight` (0–2000 или null), `warmup_sets` (boolean), `instructions`;
- методы подходов: `set_type` — `normal`, `superset`, `dropset`, `rest_pause`, `cluster`, `amrap`; `group_id` связывает элементы группы.

Одинаковые `exercise_id` и `order` в одном плане запрещены. Поля `name` и настройки справочника используются только при подтверждённом создании неизвестного упражнения; существующая запись по `exercise_id` не перезаписывается импортом.

## Серверный поток импорта

1. Сервер проверяет upload error, расширение `.json`, MIME и лимит `MAX_UPLOAD_BYTES` (по умолчанию 1 МиБ).
2. JSON разбирается с ограничением глубины, затем строго проверяются типы, диапазоны, закрытые наборы полей, схема и версия.
3. Preview показывает дату, тип, программу, причину версии, шаблон и полный список упражнений.
4. Глобальные и принадлежащие пользователю активные `exercise_id` считаются доступными. Неактивные блокируют импорт. ID чужого пользовательского упражнения блокирует импорт без раскрытия чужих данных.
5. Неизвестные упражнения создаются только после отдельного обязательного checkbox-подтверждения и получают `owner_user_id` текущего пользователя.
6. В одной транзакции сохраняются неизвестные упражнения, программа, версия, шаблон, план, плановые упражнения и audit log. Любая ошибка откатывает всё.
7. Повторный `plan_id` проверяется в пределах текущего пользователя и не удаляет/не обновляет ранее импортированный план.

Исходный канонический JSON хранится в `workout_plans.source_json`. Снимки версии и шаблона имеют SHA-256 хеши, которые защищают исторические записи от молчаливого изменения.

## Негативные fixtures

- `invalid-json.json` — синтаксически битый JSON;
- `wrong-schema.json` — документ другого типа;
- `unexpected-field.json` — лишнее поле в закрытом объекте;
- `duplicate-exercise.json` — повтор стабильного `exercise_id`.

Они находятся рядом с валидным примером в `tests/fixtures/training-plan/` и запускаются командой `php tests/stage2.php`.

# JSON-формат отчёта тренировки

## Контракт training-report v1.0

Экспорт завершённой тренировки возвращает UTF-8 JSON с маркерами:

```json
{"schema":"training-report","schema_version":"1.0"}
```

Машиночитаемый корневой контракт находится в `docs/training-report-v1.0.schema.json`; серверный `ReportService` остаётся источником фактической сериализации.

Версия `1.0` неизменяема по смыслу: несовместимое расширение получает новую `schema_version`. Все поля времени событий имеют суффикс `_utc` и формат RFC 3339 с `Z`. План, факт и рекомендация никогда не объединяются и не перезаписывают друг друга.

## Корневой объект отчёта

| Поле | Тип | Назначение |
|---|---|---|
| `schema`, `schema_version` | string | Идентичность контракта |
| `generated_at_utc` | datetime | UTC-время формирования конкретного файла |
| `plan` | object | Неизменяемая идентичность и задача исходного плана |
| `session` | object | Время, итоговые оценки, комментарий и признаки редактирования |
| `readiness` | object | Состояние до тренировки и исходный комментарий |
| `exercises` | array | Раздельные `planned`, `fact`, `suggestion` по упражнениям |
| `summary` | object | Итоговые метрики, PR и сравнение с прошлой такой тренировкой |
| `edits` | array | Audit trail относящихся к сессии, упражнениям и подходам действий |

`plan` содержит `plan_id`, `name`, `date`, `type`, `goal`, `trainer_notes`. `session` содержит стабильный `session_id`, `status`, `started_at_utc`, `finished_at_utc`, `duration_minutes`, `session_rpe` 1–10, `wellbeing` 1–5, `comment`, `edited_after_completion`, `edited_at_utc`.

## Упражнение: planned / fact / suggestion

Каждый элемент `exercises` имеет общий фактический `exercise_id` и отображаемое `name`, а также три независимые части:

- `planned`: исходное упражнение, количество подходов, `rep_range`, `target_rir`, отдых, запланированный вес, метод и инструкция;
- `fact`: фактический ID/название, статус, структурированный пропуск, замена, подходы, метрики, оценка, комментарий, дискомфорт и PR;
- `suggestion`: `null` либо отдельное предложение double progression с `current_weight_kg`, `suggested_weight_kg`, `accepted_weight_kg`, статусом, причиной и временем решения.

`suggestion.program_changed` в v1.0 всегда `false`: принятие предложения фиксирует решение пользователя, но не меняет `workout_plans`, `workout_exercises`, программу или её версию. Новая программа создаётся отдельным будущим действием.

Фактический подход содержит:

```json
{
  "set_id": "set-...",
  "set_number": 1,
  "type": "working",
  "method": "normal",
  "weight_kg": 60.0,
  "reps": 10,
  "rir": 2.0,
  "performed_at_utc": "2026-08-24T10:00:00Z",
  "edited_at_utc": null
}
```

Разминка экспортируется, но `tonnage_kg`, `working_sets` и `average_rir` считают только неудалённые `working` sets. `best_e1rm` имеет поля `e1rm_kg`, `weight_kg`, `reps` и рассчитывается по Epley: `weight × (1 + reps / 30)`. Это аналитическая оценка, а не фактический максимум.

`fact.substitution` хранит исходный и фактический ID, причину и UTC-время. `fact.skip` хранит структурированную причину. Каждый объект `discomfort` содержит область, интенсивность 1–10, комментарий и UTC-время. Комментарии readiness, упражнения и сессии остаются в своих контекстах.

## Итог, PR и сравнение

`summary` содержит:

- `completed_exercises`, `skipped_exercises`, `total_exercises`;
- `working_sets`, `tonnage_kg`, `average_rir`;
- `personal_records` — только новые ориентиры этой сессии;
- `comparison_with_previous` — `null` либо ID/дата предыдущей такой тренировки и дельты длительности, рабочих подходов, tonnage и среднего RIR.

Для поиска предыдущей тренировки используется тот же неизменяемый шаблон, а для старых/ручных планов без template ID — совпадающие имя и тип. PR `best_e1rm` создаётся только при превышении лучшего предыдущего e1RM этого пользователя и упражнения. Повторная доставка завершения и повторный пересчёт не создают дубликатов.

## Редактирование и audit trail

После правки завершённой тренировки `session.edited_after_completion=true`, `edited_at_utc` получает время последней правки, а `edits` содержит `entity_type`, `entity_id`, `action`, снимки `before`/`after` и `at_utc`. После изменения подхода метрики, ожидающие предложения прогрессии и PR пересчитываются; исходный план остаётся неизменным.

## Markdown и оба файла

- `.json` — полный машинный контракт для анализа и повторного парсинга;
- `.md` — читаемое представление с явными секциями «План», «Факт», «Предложение» для прямой вставки в ChatGPT;
- `.zip` — ровно один JSON и один Markdown с одинаковым базовым именем сессии.

Все три маршрута требуют авторизации и фильтруют сессию по текущему `user_id`. Интеграционные и round-trip проверки запускаются командой `php tests/stage5.php`.

# JSON-формат отчёта плавания

## Контракт swimming-report v1.0

Авторизованный маршрут `/export/swimming/{id}.json` возвращает:

```json
{"schema":"swimming-report","schema_version":"1.0"}
```

Машиночитаемая корневая схема находится в `docs/swimming-report-v1.0.schema.json`. `session` содержит стабильный ID, локальную дату, `occurred_at_utc`, длительность, длину бассейна, общую дистанцию, основной стиль, интенсивность, fatigue рук/спины/ног, самочувствие, комментарий, источник, расписание и версию правки.

`intervals` — упорядоченный массив блоков: `repeat_count`, `distance_m` за повтор, рассчитанный `total_distance_m`, стиль, необязательные интенсивность/отдых/заметка. Сумма блоков уже проверена сервером и равна общей дистанции.

`training_sequence` содержит последние силовые и плавательные события пользователя с типом, стабильным ID, UTC-временем, подписью и дистанцией для плавания. Поле `interpretation` в v1.0 всегда `null`: экспорт показывает последовательность для будущего внешнего анализа, но не формирует физиологических или медицинских выводов. Markdown доступен по `/export/swimming/{id}.md`.

Backup v1.1 включает `swimming_sessions`, `swimming_intervals`, `schedules` и вычисленную `training_sequence`; после restore последовательность всё равно заново вычисляется из фактических записей. Все выборки ограничены текущим `user_id`.

# JSON-формат резервной копии

## Контракт training-diary-backup v1.1

Корень содержит ровно шесть полей:

```json
{
  "schema": "training-diary-backup",
  "schema_version": "1.1",
  "backup_id": "backup-0123456789abcdef0123456789abcdef",
  "exported_at_utc": "2026-08-24T10:00:00Z",
  "checksum_sha256": "sha256 канонического объекта data",
  "data": {}
}
```

`data` обязан содержать все секции v1.1: пользовательские упражнения, программы/версии/шаблоны/versioned schedule slots/планы, плановые и фактические упражнения, сессии/readiness/подходы/дискомфорт/прогрессию/PR, измерения, обычное расписание, плавание/интервалы и audit. В `training_programs` переносится `active_version_id`, в `program_versions` — lifecycle/lock/hash/timestamps, а отдельная секция `program_schedule_slots` хранит weekday → template внутри версии. Пароль, login attempts, cookie/session, offline receipts и technical `assistant_tool_calls` не экспортируются.

Restore также принимает точный legacy-контракт v1.0 без `program_schedule_slots` и новых lifecycle-полей. Такие версии восстанавливаются как `published` с `aggregate_hash=snapshot_hash`; pointer выставляется автоматически только при одной версии. Если legacy-программа содержит несколько версий, `active_version_id` остаётся `NULL` до явного reconciliation.

Сервер сначала ограничивает размер upload, для ZIP требует ровно один безопасно названный JSON и проверяет размер распакованного содержимого. Затем проверяются точный набор корневых полей/секций, обязательные скалярные идентификаторы, лимит числа строк, версия и checksum. Только после этого backup хранится во временной PHP-сессии и показывается preview.

Подтверждение запускает только `merge`: существующие стабильные сущности пропускаются, никакие строки не перезаписываются и не удаляются. Внутренние ID, active pointer и slot-ссылки переназначаются в порядке зависимостей; tenant-поля принудительно получают текущий `user_id`. Parent version, active version и template каждого slot обязаны принадлежать ожидаемой программе/версии. Ошибка связи, конфликт пользовательского `exercise_id` или SQL-ошибка откатывает транзакцию. Повтор того же checksum в пределах пользователя идемпотентен.
