# База данных Ритма

## Общие правила

Схема находится в `database/schema.sql`, начальный справочник — в `database/seed.sql`. Все таблицы используют InnoDB и `utf8mb4`. События записываются через `UTC_TIMESTAMP()`; timezone пользователя хранится в `users.timezone` и применяется только при отображении.

Новая база устанавливается командой `php bin/install.php`. Seed идемпотентен: существующие стабильные `exercise_id` не перезаписываются.

## Группы сущностей

- доступ: `users`, `login_attempts`;
- справочник: `exercises`, где системные записи имеют `owner_user_id = NULL`, пользовательские — владельца; `exercise_id` является глобально уникальным и неизменяемым, а `status` и `progression_increment`/`progression_mode` задают доступность и шаг прогрессии;
- план: `training_programs`, `program_versions`, `workout_templates`, `program_schedule_slots`, `workout_plans`, `workout_exercises`;
- факт: `workout_sessions`, `readiness_logs`, `session_exercises`, `exercise_sets`;
- обратная связь: `discomfort_logs`, `progression_suggestions`, `personal_records`;
- дополнительные данные: `body_measurements`, `swimming_sessions`, `schedules`, `audit_logs`, `backup_restores`;
- доставка offline-команд: `offline_action_receipts`.

Плановые и фактические данные разделены. `training_programs.external_program_id` стабильно идентифицирует программу в пределах пользователя, а nullable `active_version_id` является единственным источником истины для текущей версии. Составной FK `(active_version_id, id) → program_versions(id, program_id)` запрещает ссылку на версию другой программы. `NULL` при нескольких версиях означает не «последнюю по номеру», а явную необходимость reconciliation.

`program_versions` хранит номер, читаемую причину, `parent_version_id`, канонический `snapshot_json`/`snapshot_hash`, lifecycle `draft/published/archived`, optimistic `lock_version`, `aggregate_hash` и lifecycle timestamps. Исторические версии после миграции считаются `published`; импорт не обновляет существующую версию. `workout_templates` неизменяемы внутри версии по паре `(program_version_id, code)` и защищены `content_hash`. `program_schedule_slots` фиксирует историческое недельное расписание версии: один template на weekday, максимум один slot на `(program_version_id, weekday)`. Составной FK не позволяет связать slot с template другой версии. Конкретный `workout_plan` ссылается и на версию, и на шаблон, но отдельно хранит дату и исходный JSON. Исторически важные сущности имеют `deleted_at`; конкурентное редактирование защищено `version` у `workout_sessions`, `session_exercises` и `exercise_sets`.

## Online-поток тренировки

Старт блокирует принадлежащий пользователю `workout_plan`, повторно использует его незавершённую сессию или атомарно создаёт `workout_session`, `readiness_log` и снимок `session_exercises`. `session_exercises` хранит исходное и фактическое упражнение, причину/время замены, статус и оценку. Допустимые статусы: `pending`, `active`, `waiting`, `completed`, `skipped`.

Каждый подход проходит строгую validation и сохраняется в `exercise_sets`. Пара `(set_type, set_number)` не смешивает warmup с working; tonnage считает только `working`. Изменение подхода увеличивает его `version`, увеличивает версию сессии и пишет before/after в `audit_logs`.

Все изменяющие workout API требуют `client_action_id`. `offline_action_receipts` хранит тип действия и его JSON-результат с уникальностью `(user_id, client_action_id)`. Перед проверкой версий сервер блокирует строку пользователя и ищет receipt: поэтому повторная доставка возвращает исходный результат, не повторяет mutation и не создаёт второй audit/progression/discomfort. Повтор того же ключа с другим типом отклоняется. Старый `exercise_sets.client_action_id` сохранён как дополнительная совместимость для подходов, созданных до миграции этапа 4.

Все существенные действия сначала блокируют сессию по `(id, user_id)`, сравнивают присланную `session_version`, затем увеличивают её. Замена и дискомфорт дополнительно сравнивают `session_exercises.version`. Несовпадение возвращается API как HTTP 409 и не перезаписывает свежие данные другой вкладки.

## Изоляция пользователей

Корневые пользовательские сущности содержат `user_id` и индекс по владельцу. Репозитории сначала проверяют владельца корневой записи, а дочерние данные загружают только после этой проверки. JOIN между сессией и планом дополнительно связывает одинаковый `user_id`. Глобальные упражнения доступны всем, пользовательские — только владельцу.

Любой новый запрос обязан принимать текущий `user_id` с сервера: идентификатор из URL или JSON сам по себе не является проверкой доступа. Для изменяющих действий дополнительно обязателен CSRF и транзакция, если меняется несколько связанных записей.

## Критические ограничения и индексы

- уникальные login и email;
- rate limit по `(attempt_key, attempted_at)` и `(ip_address, attempted_at)`;
- уникальный внешний ID программы и плана в пределах пользователя;
- уникальная версия программы;
- уникальный код и хеш содержимого шаблона внутри версии;
- уникальная позиция упражнения/подхода;
- идемпотентность offline-действия через `(user_id, client_action_id)`;
- индексы по владельцу, статусу и дате для Dashboard и истории;
- внешние ключи между планом, фактом, справочником и аудитом.

## Миграции

`database/migrations/001_initial.sql` документирует начальную версию и не переписывается. Для существующей БД миграции применяются по порядку. `006_stage_6_analytics.sql` добавляет индексы истории и агрегатов. `007_stage_7_swimming_schedule.sql` версионирует расписание и плавание. `009_webmcp_foundation.sql` добавляет минимизированный technical audit. `010_program_version_lifecycle.sql` добавляет lifecycle, active pointer и versioned schedule slots; автоматически связывает только программы с одной версией. После dry-run `php bin/reconcile-program-versions.php` безопасные single-version cases можно применить через `--apply`; ambiguous cases команда только показывает. Для новой установки источником истины остаётся актуальный `database/schema.sql`.

## Плавание и расписание

`swimming_sessions` — пользовательский корень факта плавания. Он хранит `public_id`, локальную `swim_date`, рассчитанную в timezone пользователя `occurred_at` в UTC, длительность, бассейн, общую дистанцию, стиль, интенсивность, три fatigue-оценки, самочувствие, комментарий, источник и `version`. Ссылка на `schedule_id` разрешена только для активной записи типа `swimming` того же пользователя и совпадающего дня недели.

`swimming_intervals` — упорядоченные блоки с `repeat_count`, метрами за повтор, стилем, необязательной интенсивностью, отдыхом и заметкой. Сервер требует, чтобы каждый блок состоял из целых длин бассейна, а сумма `repeat_count × distance_m` точно равнялась `swimming_sessions.total_distance_m`. Таблица не связана с `exercise_sets`: силовой tonnage/RIR к плаванию не применяются.

`schedules` содержит не более одной строки на `(user_id, weekday)`. При регистрации создаются активные defaults: понедельник/среда `strength`, четверг `swimming`; для существующего пользователя тот же набор лениво создаётся при первом открытии расписания. Замена недели выполняется транзакционно и фиксируется в `audit_logs`.

Общая хронология строится `UNION ALL` двух ограниченных по `user_id` источников: завершённых `workout_sessions` и `swimming_sessions`. На уровне выдачи унифицируются только дата, тип, ссылка и подпись; силовые sets/tonnage/RIR не синтезируются для плавания.

## Backup и restore v1.0/v1.1

Новый export использует формат v1.1 и добавляет `program_schedule_slots`, lifecycle-поля версий и `active_version_id`. Restore продолжает строго принимать legacy v1.0; единственная восстановленная legacy-версия безопасно связывается как active, а несколько версий остаются неоднозначными. Technical-таблица `assistant_tool_calls`, пароль, PHP-сессия и `login_attempts` в backup не входят. Backup выгружает только строки текущего пользователя и принадлежащие им дочерние строки. Данные отсортированы детерминированно; SHA-256 считается по каноническому объекту `data` и проверяется до preview.

Restore всегда работает в одной транзакции и только в режиме безопасного merge. Корневые записи ищутся по стабильным ключам (`external_program_id`, `external_plan_id`, `public_id`, weekday), существующие строки пропускаются и никогда не обновляются/удаляются. Числовые ID из backup считаются только локальными ссылками файла: для каждой таблицы строится old→new map, включая active pointer и slots. Любой `user_id`/`owner_user_id` из файла игнорируется и заменяется ID текущей сессии; parent/active/template связи дополнительно проверяются на принадлежность одной программе и версии. Недоступная или cross-tenant связь откатывает всю операцию.

`backup_restores` имеет уникальность `(user_id, checksum_sha256)`. Поэтому повторная доставка того же файла возвращает сохранённый summary и не дублирует данные/audit, а одинаковый checksum у другого пользователя остаётся отдельным tenant. Restore добавляет `audit_logs.action=restore_merge` после успешного merge.

Исторические подходы, измерения и плавание удаляются только через `deleted_at` после явного подтверждения; before-снимок и `soft_delete` сохраняются в audit. Отмена незавершённой тренировки меняет статус сессии на `cancelled`, но не стирает подходы и снова делает план доступным.

Миграция `008_stage_8_backup_restore.sql` добавляет restore receipts и составные индексы планов/audit. `bin/cleanup.php` удаляет login attempts старше 30 дней, offline receipts старше 90 дней и файлы cache старше 7 дней; запуск предполагается по cron после ручной проверки.

## Транзакция импорта v1.0

Транзакция создаёт в порядке зависимостей пользовательские неизвестные упражнения, `training_program`, `program_version`, `workout_template`, `workout_plan`, `workout_exercises` и `audit_log`. Проверки доступности упражнений и дубликата выполняются повторно непосредственно перед записью. Ошибка родительской версии, конфликт хеша, шаблона или `plan_id` откатывает все промежуточные вставки. Дубликат проверяется по `(user_id, external_plan_id)`, поэтому одинаковые внешние ID разных пользователей не пересекаются.
