## 1. Решение по организации работ

Пункты 7–10 нужно рассматривать как один редизайн экрана активной тренировки, но реализовывать последовательными интеграционными этапами в отдельных чатах. Делить работу буквально на четыре независимых пункта и выполнять параллельно нельзя: карточка, график, колёсики и карусель меняют одни и те же DOM-узлы, CSS и состояние черновика, а жесты колёсиков и карусели должны проектироваться совместно.

Единицей интеграции остаётся текущая ветка проекта. Каждый следующий чат начинает работу после завершения, проверки и коммита предыдущего этапа. Этот файл служит общим контрактом и журналом статуса, чтобы новый чат не зависел от контекста предыдущего.

Рекомендуемая последовательность:

1. Контракт и серверные данные истории.
2. Новая оболочка карточки, график, сворачивание и пиктограммы.
3. Три вертикальных колёсика ввода.
4. Карусель-стопка, навигация и арбитраж жестов.
5. Сквозная стабилизация, PWA/offline, доступность и приёмка на iPhone.

Отдельно можно подготовить набор SVG-пиктограмм после фиксации контракта имён файлов, но подключать его к карточкам следует только на втором этапе. Остальные этапы не выполнять параллельно.

## 2. Зафиксированное состояние проекта

- Серверный рендеринг: `views/sessions/workout.php`.
- Основная клиентская логика экрана: `public/assets/workout.js` (около 700 строк).
- Стили экрана: `public/assets/workout.css`.
- Данные активной сессии: `App\Repository\TrainingRepository::session()`.
- Offline-черновик уже хранит введённые вес, единицу, повторы, RIR и тип подхода через `captureDraft()`/`restoreDraft()`.
- Общий таймер отдыха расположен вне карточек и уже переживает переключения состояния экрана.
- Закреплённый общий прогресс реализован; единицы kg/lb, возобновление, события отдыха и Web Push покрыты отдельными тестами.
- Текущая история `previous_sets` — плоский список максимум из пяти подходов. В нём нет группировки по тренировкам, даты и исторической цели RIR, поэтому он непригоден для пункта 8.
- Историческую цель RIR можно получить без миграции: она уже хранится в неизменяемом `workout_exercises`, связанном с каждым прошлым `session_exercises`.
- В проекте нет D3 и корневого JS build pipeline. CDN-зависимость из макета нельзя переносить в offline-first PWA.
- В текущей разметке нет управления сворачиванием карточки и сохранения раскрытого состояния. Несмотря на общий статус «пункты 1–6 выполнены», при реализации пунктов 9–10 нужно также закрыть и повторно проверить критерии пункта 3, от которых они зависят.
- В каталоге упражнений нет поля пиктограммы. Для первой версии достаточно локального allow-listed набора файлов по стабильному `exercise_id` и общей запасной пиктограммы; миграция БД для этого не нужна.

Перед началом каждого этапа обязательно проверить `git status` и не перезаписывать несвязанные изменения пользователя.

## 3. Целевая архитектура

### 3.1. Модули клиента

Не расширять `workout.js` всей новой логикой. Вынести чистую и тестируемую механику в небольшие локальные модули по образцу `weight.js` и `rest-timer.js`:

- `public/assets/workout-history.js` — подготовка рядов, цвет RIR, расчёт видимого окна, SVG-график и детализация подхода;
- `public/assets/workout-wheel.js` — модель значения, шаг, округление, виртуализированное окно значений и DOM-контрол колёсика;
- `public/assets/workout-card.js` — состояние раскрытия карточек и вспомогательные операции заголовка/пиктограммы;
- `public/assets/workout-carousel.js` — индекс активной карточки, границы, направление жеста и переходы.

`workout.js` остаётся интеграционным координатором: очередь offline-действий, снимок сессии, формы, таймер и связывание модулей с DOM. Модули должны экспортировать чистые функции через CommonJS для Node-тестов и одновременно предоставлять браузерный глобальный объект, как существующие модули проекта.

Все новые файлы подключаются локально и добавляются в app shell Service Worker. При изменении app shell версия кеша повышается один раз на законченном этапе.

### 3.2. Контракт истории упражнения

Вместо `previous_sets` каждое упражнение получает поле следующего смысла:

```text
history_sessions[]
  session_id
  scheduled_date
  target_rir_min | null
  target_rir_max | null
  sets[]
    set_id
    set_number
    weight_kg
    weight_value
    weight_unit
    reps
    rir | null
```

Правила контракта:

- только завершённые прошлые тренировки этого пользователя и фактически выполненного упражнения;
- текущая сессия исключена;
- только рабочие и не удалённые подходы;
- одна группа соответствует одной тренировке, подходы внутри упорядочены стабильно;
- не более шести последних тренировок на упражнение, выдача от старой к новой для рисования;
- цель RIR берётся из плана именно той исторической тренировки; текущую цель не подставлять;
- исходные `weight_value`/`weight_unit` и нормализованный `weight_kg` передаются вместе;
- отсутствие данных выражается пустым массивом, а не фиктивными столбцами.

Чтобы не делать неограниченный общий запрос и не зависеть от оконных функций конкретной версии MySQL/MariaDB, допустима схема: получить уникальные упражнения текущей сессии, для каждого ограниченно выбрать последние шесть исторических `session_exercises`, затем одним запросом получить подходы для собранных идентификаторов. Количество упражнений в тренировке мало и ограничено предметной областью.

### 3.3. Состояние UI в offline-черновике

Расширить черновик обратносуместимым полем:

```text
ui
  activeExerciseId
  expandedExerciseIds[]
  selectedHistorySessionByExercise {}
```

Отсутствующее `ui` в старом черновике означает: первая незавершённая карточка активна, все карточки свёрнуты, для графика выбрана последняя тренировка. Переключение карточки или раскрытие не является серверной мутацией и не меняет версию сессии.

Черновики самих колёсиков продолжают сохраняться в существующих полях формы, чтобы обновление приложения и восстановление offline не теряли выбранные значения.

### 3.4. Пиктограммы

- Каталог: `public/assets/exercises/`.
- Имена: `<exercise_id>.svg` только для известных стабильных идентификаторов.
- Обязательный `generic.svg` для пользовательских и ещё не отрисованных упражнений.
- Для 14 seed-упражнений подготовить единый монохромный/двухцветный набор с одинаковым viewBox, толщиной линий, безопасными полями и без текста.
- PHP должен выдавать только проверенный локальный URL: разрешённый формат имени плюс существующий файл, иначе `generic.svg`.
- При замене упражнения пиктограмма и `alt` обновляются вместе с названием и единицей веса.
- SVG не должен содержать скрипты, внешние ссылки или встроенные растровые data URI.

## 4. Этапы для отдельных чатов

### Этап 1. Серверный контракт истории

Объём:

- заменить плоский `previous_sets` структурированным `history_sessions`;
- добавить исторические дату, целевой диапазон RIR и все значения каждого рабочего подхода;
- сохранить текущую логику предзаполнения формы: она берёт последний подход последней исторической тренировки, если в активной сессии ещё нет подходов;
- не менять внешний вид карточки на этом этапе;
- при необходимости временно адаптировать строку «В прошлый раз» к новому контракту, чтобы экран оставался рабочим до этапа 2.

Тесты:

- группировка по тренировкам и порядок;
- максимум шесть тренировок на упражнение;
- исключены текущая сессия, разминка, soft-deleted set и чужой пользователь;
- разные веса внутри тренировки и смешанные kg/lb;
- дробный RIR и диапазон цели;
- неизвестная историческая цель остаётся `null`;
- предзаполнение не регрессирует.

Готово, когда серверные и существующие workout/weight тесты проходят, а активная тренировка открывается с прежним вводом.

### Этап 2. Карточка, график, сворачивание и пиктограммы

Объём:

- перестроить верх карточки по утверждённому PNG: пиктограмма слева, номер/название/статус, компактные плашки веса, плана и RIR, рядом отдых;
- добавить семантическую кнопку раскрытия с `aria-expanded` и связью через `aria-controls`;
- при первом открытии все формы ввода свёрнуты; раскрытие независимо для каждой карточки и сохраняется в `draft.ui`;
- сохранённые подходы и форма находятся в раскрываемой части, их данные не уничтожаются при сворачивании;
- заменить строку «В прошлый раз» компактным локальным SVG-графиком без D3;
- реализовать кирпичики повторений, сетку через 3, общий уровень подписей веса, линии к столбцам, RIR у основания, единицу один раз, даты и легенду;
- классифицировать цвет относительно исторического диапазона: ниже — красный, внутри — зелёный, выше — голубой, неизвестно — серый;
- по нажатию/клавиатуре на подход показывать точные вес, повторы и RIR;
- на узкой ширине показывать доступное число целых групп и переключать историю явными кнопками/датами, без горизонтального свайпа;
- подключить локальные SVG-пиктограммы и fallback.

Доступность:

- график имеет текстовое резюме и доступные кнопки подходов, смысл не передаётся только цветом;
- состояние раскрытия озвучивается;
- длинное имя не выталкивает статус и кнопку за экран;
- пустая история имеет компактное осмысленное состояние.

Тесты:

- чистая функция сравнения RIR с одиночной целью/диапазоном/null;
- расчёт видимого окна при разных ширинах и числе тренировок;
- построение доступного текста подхода;
- сохранение/восстановление раскрытия;
- fallback пиктограммы и безопасное имя файла;
- статическая проверка разметки, ARIA, локальных ассетов и отсутствия CDN.

Готово, когда карточка соответствует утверждённой композиции на 320, 390 и 430 px, но пока остаётся в обычном вертикальном списке.

### Этап 3. Три вертикальных колёсика

Объём:

- заменить основную форму чисел тремя визуальными колёсиками Вес → Повторы → RIR;
- выбранные значения расположить на одной горизонтальной линии и синхронизировать с существующими полями payload;
- вес использует шаг выбранного упражнения/единицы (`RhythmWeight.step()` в текущем поведении: kg 0,5; lb 5), повторы — 1, RIR — 0,5;
- сохранить рабочий/разминочный переключатель и существующий submit/offline pipeline;
- по нажатию на выбранное значение открыть точный ручной ввод; после подтверждения нормализовать значение, но не терять допустимые дроби;
- не создавать тысячи DOM-узлов на каждую карточку: использовать виртуализированное/переиспользуемое окно значений и инициализировать контрол только в раскрытой активной области;
- единица kg/lb остаётся доступна рядом с весом, смена единицы использует уже существующую серверную мутацию и обновляет шаг;
- после сохранения подхода очистить только RIR согласно текущему поведению; вес и повторы остаются удобным предзаполнением;
- `touch-action` на кнопках исключает double-tap zoom, но viewport не запрещает pinch zoom.

Доступность:

- каждое колёсико имеет имя, текущее значение и клавиатурные команды;
- предусмотрены явные кнопки уменьшения/увеличения или эквивалент для пользователей без свайпа;
- ручной input остаётся настоящим `input` с валидацией;
- VoiceOver может изменить и подтвердить значение без точного жеста прокрутки.

Тесты:

- границы, шаг и округление kg/lb;
- RIR 1,5 и другие половинные значения;
- ручное значение, восстановление draft и переключение единицы;
- один submit создаёт ровно один `set.create` и запускает один таймер;
- отсутствие регрессии в offline queue и optimistic restore;
- отсутствие разрастания DOM пропорционально полному диапазону веса.

Готово, когда колёсики полностью работают в вертикальном списке карточек. Карусель намеренно добавляется позже.

### Этап 4. Карусель-стопка и арбитраж жестов

Объём:

- превратить `.exercise-stack` в карусель с одной активной карточкой и декоративно видимыми краями соседних;
- добавить позицию «Упражнение N из M» отдельно от счётчика завершённых;
- по позиции открывать компактный список всех упражнений с пиктограммой и статусом для прямого перехода;
- добавить явные кнопки назад/вперёд, корректные disabled-состояния первой и последней карточки;
- начальная карточка — сохранённая из draft, иначе первая незавершённая/непропущенная, иначе первая;
- переключение не отправляет серверную мутацию, не меняет порядок, не создаёт подход и не сбрасывает раскрытие/ввод;
- общий таймер остаётся вне карусели и виден во время переходов;
- finish-card и опасная зона остаются доступны вне карусели.

Арбитраж жестов:

- карусель слушает Pointer Events и после небольшого порога один раз фиксирует намерение жеста;
- горизонтальное направление принимается только при явном преобладании `abs(dx)` над `abs(dy)`;
- путь события внутри колёсика, ручного input, графика, диалога или другого интерактивного элемента не запускает карусель;
- вертикальный жест внутри колёсика меняет только колёсико;
- вертикальный жест вне колёсиков прокручивает содержимое текущей карточки/страницы;
- один жест никогда не меняет и колёсико, и карточку;
- при `prefers-reduced-motion` переход мгновенный или минимальный;
- история не получает собственного горизонтального свайпа.

Тесты:

- reducer индекса, границы и прямой переход;
- функция определения направления на горизонтальных, вертикальных и диагональных траекториях;
- игнорирование интерактивных потомков/колёсика;
- сохранение активной карточки и раскрытий в draft;
- клавиатура, список и кнопки дают тот же результат, что свайп;
- замена упражнения и изменение статуса обновляют список и активную карточку;
- быстрые переходы не прерывают таймер и не дублируют действия очереди.

Готово, когда полный сценарий работает мышью, клавиатурой и touch-эмуляцией без физического iPhone.

### Этап 5. Сквозная стабилизация и приёмка

Объём:

- прогнать весь существующий PHP/Node набор и новые тесты;
- проверить fresh load, reload, offline reload, очередь pending, HTTP 409 и обновление Service Worker;
- проверить состояния: нет истории, одна/шесть тренировок, разное число подходов, длинные названия, замена, ожидание, completed, skipped;
- проверить темы light/dark, RU/EN, safe area, 200% zoom, VoiceOver/клавиатуру и reduced motion;
- проверить отсутствие горизонтального overflow на 320/390/430 px;
- провести реальную приёмку в установленной PWA на iPhone: вертикальные колёсики, горизонтальная карусель, диагональные жесты, double tap, pinch zoom, блокировка/возврат, таймер и offline;
- исправлять только интеграционные дефекты пунктов 7–10; новые продуктовые идеи вынести отдельно.

Обязательные сценарии iPhone:

1. Раскрыть карточку, выставить вес/повторы/RIR, перелистнуть и вернуться — всё сохранено.
2. Быстро крутить каждое колёсико по вертикали — карточка не меняется.
3. Делать диагональные движения на колёсике и рядом с ним — срабатывает только определённое намерение.
4. Переключать упражнения во время активного отдыха — таймер не сбрасывается.
5. Уйти в фон, вернуться, перезагрузить offline — карточка, draft и таймер восстанавливаются.
6. Изменить kg/lb, вручную ввести дробный вес и RIR 1,5, сохранить и проверить историю.
7. Проверить первую/последнюю карточку, список прямого перехода, VoiceOver и Reduce Motion.

Физическая приёмка на iPhone является release gate. Автоматические тесты и браузерная эмуляция её не заменяют.

## 5. Общие критерии качества

- Не менять серверные payload `set.create`, weight-unit mutation, status actions и rest timer без отдельной причины и тестов.
- Не ломать offline-first порядок: локальная запись создаётся до сетевого запроса, зависимые действия сохраняют порядок и idempotency.
- Не использовать CDN, удалённые шрифты, runtime-загрузку графической библиотеки или небезопасный inline SVG из данных БД.
- Не добавлять `user-scalable=no` и не отключать pinch zoom.
- Все новые видимые строки должны пройти через существующую локализацию RU/EN.
- Изменение Service Worker всегда сопровождается версией кеша и тестом app shell.
- Любой новый UI-state должен быть совместим со старым draft без миграции IndexedDB.
- История и цвет никогда не используют текущую цель вместо неизвестной исторической.
- Переход между карточками не является изменением бизнес-состояния упражнения.
- Коммиты этапов оформлять на русском языке.

## 7. Правила передачи между чатами

В конце каждого этапа чат обязан:

1. Обновить таблицу статуса ниже.
2. Записать имена изменённых файлов, фактически выполненные проверки и оставшиеся ограничения.
3. Создать один логически цельный коммит с русским сообщением, если пользователь не попросил иначе.
4. Не начинать следующий этап в том же чате, если он заметно расширяет контекст; следующий чат читает этот файл, исходный план и последний коммит.
5. Не считать физическую проверку iPhone выполненной без подтверждения пользователя или реального доступа к устройству.
