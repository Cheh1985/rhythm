# Offline-first и идемпотентность

## Карта изменяющих API-действий

Карта составлена до реализации этапа 4. Клиент создаёт UUID один раз, сохраняет действие в IndexedDB и при каждом повторе отправляет тот же `client_action_id`. Сервер хранит результат в `offline_action_receipts` с уникальностью `(user_id, client_action_id)`.

| Действие | Маршрут | Тип ключа | Зависимость |
|---|---|---|---|
| Начать тренировку | `POST /api/sessions` | UUID `session.start` | план; повторный старт также ограничен одной активной сессией плана |
| Добавить подход | `POST /api/sessions/{id}/sets` | UUID `set.create` | активная сессия и упражнение |
| Изменить подход | `PATCH /api/sets/{id}` | UUID `set.update` | ранее созданный/серверный подход |
| Изменить статус упражнения | `PATCH /api/sessions/{id}/exercise-status` | UUID `exercise.status` | активная сессия; порядок переходов статуса |
| Заменить упражнение | `PATCH /api/sessions/{id}/replace-exercise` | UUID `exercise.replace` | активная сессия и версия упражнения |
| Записать дискомфорт | `POST /api/sessions/{id}/discomfort` | UUID `discomfort.create` | активная сессия и упражнение |
| Завершить тренировку | `POST /api/sessions/{id}/finish` | UUID `session.finish` | все предшествующие локальные действия сессии |

`client_action_id` идентифицирует намерение, а не сетевую попытку. Повтор с тем же ключом и другим типом действия отклоняется. Outbox хранит явный `depends_on` и отправляется устойчивой топологической сортировкой; действия одной сессии дополнительно образуют последовательную цепочку.

## Локальные данные

IndexedDB `rhythm-offline-v1` содержит:

- `sessions` — последний серверный снимок активной сессии и локальные фактические изменения;
- `outbox` — тело запроса, UUID, зависимости, состояние и диагностическую ошибку;
- `meta` — активный пользователь, lease fallback и служебная версия.

Все ключи начинаются с `user:{id}:`. При logout клиент удаляет namespace, пользовательский navigation-cache и отправляет Service Worker команду очистки. Сервер дополнительно отдаёт `Clear-Site-Data` на logout. API-ответы Service Worker никогда не кеширует.

## Синхронизация и конфликты

До сетевого запроса действие и локальный снимок записываются одной IndexedDB-транзакцией. Синхронизация запускается при сохранении, событии `online`, открытии страницы и ручном retry. Web Locks разрешает отправку только одной вкладке; fallback использует короткий lease в `localStorage`. `BroadcastChannel` сообщает другим вкладкам об изменении очереди и версиях.

После успешного ответа новая версия сессии/сущности переносится в следующие ожидающие действия. HTTP 409 не удаляет действие: очередь останавливается, загружает свежий серверный снимок и показывает явный конфликт. Пользователь может либо вручную повторить своё действие поверх показанной серверной версии, либо обновить экран; локальные данные не отбрасываются автоматически.

## Service Worker и приватность

Service Worker precache-ит только публичный app shell. Навигация использует network-first. Страница активной тренировки может храниться в отдельном пользовательском cache для offline reload; этот cache очищается при logout, не используется для API и не смешивается с версионированным app shell. Generic offline fallback не содержит пользовательских данных.

Новая версия Service Worker не вызывает `skipWaiting` автоматически. Приложение сначала завершает локальную запись, показывает кнопку обновления и только по явному действию пользователя активирует новую версию. Поэтому ожидающие действия и активная тренировка переживают обновление.

## Ручной сценарий приёмки

1. Открыть тренировку онлайн и дождаться статуса «Синхронизировано».
2. В DevTools включить Offline, добавить несколько подходов и убедиться в статусе «Офлайн · ожидает синхронизации».
3. Перезагрузить страницу: ранее введённые подходы и таймер должны восстановиться.
4. Добавить ещё один подход, вернуть сеть и нажать retry при необходимости.
5. Убедиться, что очередь пуста, статус — «Синхронизировано», а в БД существует по одной записи на каждый `client_action_id`.
6. Открыть ту же тренировку во второй вкладке: отправку выполняет один sync-owner, другая вкладка получает BroadcastChannel-обновления.
7. При ожидающем новом Service Worker добавить подход offline, активировать обновление и проверить восстановление действия после reload.
8. Выйти из аккаунта и проверить отсутствие пользовательских navigation-cache и записей его namespace в IndexedDB.

## Плавание

Форма `/swimming` сохраняет полный черновик и структурированные блоки в том же пользовательском IndexedDB namespace. При отправке create/update сначала попадает в outbox с `client_action_id`, затем доставляется API. Повторная доставка возвращает receipt и не создаёт вторую сессию или второй audit. HTTP 409 при редактировании сохраняется как конфликт и не удаляет локальное действие.

После первого онлайн-посещения `/swimming`, `/swimming/{id}` и `/schedule` могут открыться из приватного navigation-cache. Для проверки: открыть форму онлайн, отключить сеть, заполнить несколько блоков, отправить, перезагрузить страницу, вернуть сеть и убедиться, что создана одна запись с теми же блоками. Logout удаляет и этот cache, и IndexedDB namespace.
