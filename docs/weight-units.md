# Единицы веса кг / lb

Исходное число и единица хранятся вместе. `1 lb = 0.45359237 kg`; сервер рассчитывает кг с восемью знаками после запятой. Переключение `50 кг → 50 lb` сохраняет число формы. Уже сохранённые подходы и план не изменяются. Кнопки ввода дают шаг 0,5 кг или 5 lb, ручной ввод допускает до двух знаков без кратности шагу.

Единица новой сессии выбирается из личного предпочтения упражнения, затем плана, затем кг. Автоподстановка последнего веса текущей сессии, предыдущей истории или плана переводит кг в единицу формы. Редактирование истории не меняет предпочтения. При замене применяется предпочтение нового упражнения; ранее записанные подходы сохраняют исходные пары.

## API и офлайн

Создание и изменение подходов принимают `weight_value` + `weight_unit`. Ответ включает также `weight_kg`. Старый запрос с одним `weight_kg` означает кг; смешивание двух форматов и неполная пара отклоняются. При частичном редактировании без веса исходная пара сохраняется.

`PATCH /api/sessions/{id}/weight-unit` принимает `session_exercise_id`, `actual_exercise_id`, `weight_unit`, `session_version`, `exercise_version`, `client_action_id`. Операция проверяет владельца, CSRF, активность сессии и версии; атомарно сохраняет единицу сессии и личное предпочтение. Повтор доставки возвращает прежний результат.

Исходная пара сохраняется в снимке IndexedDB, черновике и каждом действии очереди. Старые действия с `weight_kg` отправляются как кг. Смена единицы и подходы образуют последовательную очередь. Ожидающий подход можно исправить до отправки; во время отправки редактор сохраняет введённые значения и предлагает повторить сохранение после синхронизации. Обновление кеша приложения не удаляет IndexedDB и несинхронизированные действия.

Объём, e1RM, рекорды и сравнения используют кг. Повторы при одинаковом весе группируются по кг, округлённым до двух знаков и в PHP, и в SQL. Абсолютный шаг прогрессии остаётся в кг, процентный — в процентах. Коррекция истории попадает в аудит и пересчитывает завершённые тренировки пользователя в хронологическом порядке, сохраняя принятые решения по прогрессии.

## Форматы

- План и черновик программы v1.1: `weight` + `weight_unit` на уровне упражнения; без единицы — кг. v1.0 остаётся доступен для чтения как кг.
- Отчёт v1.1: `planned` и каждый фактический подход содержат `weight_value`, `weight_unit`, `weight_kg`; JSON, Markdown и ZIP согласованы.
- Backup v1.2: новые поля и `exercise_weight_preferences`; restore v1.0/v1.1 заполняет кг и сохраняет правила merge и изоляции пользователей.
- Site tools: исходные значения и единицы добавлены к ответам; прежние поля `_kg` сохраняют смысл. Единица в новых документах участвует в хеше. Неизменяемые старые версии не переписываются.

Схемы и пример: [описание форматов](json-format.md), [смешанный план](../tests/fixtures/training-plan/mixed-units-v1.1.json).

## Применение миграции

Миграция `015_weight_units.sql` следует после `014_demo_account.sql`. Чистая установка уже содержит новые поля. Перед применением на рабочей базе:

1. Остановить запись приложения и сделать полную резервную копию БД, включая схему; проверить возможность восстановления на отдельной базе.
2. Проверить фактические `SHOW CREATE TABLE` для `exercise_sets`, `workout_exercises`, `session_exercises`, `progression_suggestions`, `users`, `exercises`. Сверить типы ключей, движок, collation, наличие миграций 001–014 и отсутствие частично применённой 015.
3. Сохранить количество строк, количество NULL, MIN/MAX весов и контрольную выгрузку пар `id + performed_weight_kg` / `id + planned_weight_kg`. Старые значения должны помещаться в DECIMAL(7,2), нормализованные — в DECIMAL(13,8). Проверить диапазоны полей прогрессии. При расхождении фактической схемы остановиться и адаптировать миграцию по результатам проверки.
4. На отдельной MySQL/MariaDB-базе из резервной копии применить SQL, сравнить все прежние значения по ID, NULL и количества строк; проверить `weight_value=performed_weight_kg`, `planned_weight_value=planned_weight_kg`, единицы `kg`. Проверить неизменность JSON-снимков и хешей программ.
5. Проверить запись `100 lb → 45.359237 kg`, запуск сессии, импорт, backup/restore на тестовой базе. После успешной проверки повторить процедуру на рабочей базе и обновить приложение. DDL в MySQL не даёт общего транзакционного отката этой миграции; восстановление выполняется из проверенной резервной копии.

Миграция не пытается определить по числу, где раньше были введены фунты. Такие записи исправляются по одной через редактор подхода.
